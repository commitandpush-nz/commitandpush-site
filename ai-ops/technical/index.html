> THE CHRONICLE

A git repo that becomes the memory layer for your infrastructure. One entry per object (servers, services, vendors, sites, decisions, processes), built as a byproduct of normal work rather than as a documentation project.

# objects/app01.md (illustrative)
facts      Windows Server 2016 VM        [confirmed]
context    payroll API · Manchester team
relations  depends on SQL01 · used by finance
timeline   2026-03 moved to cluster B
foresight  OS support ends Jan 2027      [high]
           TLS cert renewal · lead 30d   [medium]
  • Confidence on every entry: from confirmed to hearsay, rising as evidence turns up. Claude says how sure it is.
  • Foresight: risks and things to watch, each with a horizon. An experienced engineer's instincts, written down where Claude can act on them.
  • Lexicon: your own team names, codenames and shorthand, so "Manchester" means the team, not the city.
  • update-chronicle skill: Claude checks the Chronicle when asked about something and records what it learns, through pull requests like any other change.
  • People: roles, teams and ownership only. No opinions or hearsay about individuals.
> CHANGE THROUGH CODE
  • Infrastructure as code: OpenTofu or Terraform for infrastructure, Ansible for configuration, in git.
  • Plan vs apply: Claude can run plan and open the pull request. Only the pipeline runs apply, after review.
  • Pipeline identity: its own short-lived identity via OIDC federation, not a stored key.
  • State: locked down and encrypted, because state can hold secrets.
> SECURITY MODEL
NO STANDING SECRETS
Claude uses the signed-in engineer's session (SSO, az login, gh auth) or credentials injected at runtime. Nothing pasted into chat or saved in files.
SEPARATE IDENTITIES
Discovery, engineers, the pipeline and the publishing sync each get their own, with least privilege. Short-lived over long-lived.
POINTERS, NOT SECRETS
The Chronicle records "admin password in Key Vault kv-prod, secret sql01-sa", never the value. Gitleaks and secret scanning catch slips.
UNTRUSTED INPUT
Logs, tickets and web pages can carry prompt injection. That's why every write needs human approval, whatever Claude has read.

Everything leaves a trail: git history, pipeline runs, cloud activity logs and session transcripts show who asked for what, and what changed.

> FITS WHAT YOU HAVE
  • Desktop and infrastructure: desktop support usually has plenty of data in Intune and ticket history, so Claude mines closed incidents for recurring problems and their fixes. Infrastructure usually has far less written down, so that's where the Chronicle does the heavy lifting.
  • Read-only wiki copy: a one-way sync on merge publishes to Confluence, Notion or SharePoint, filtered to leave out IPs and security notes, with a last-synced stamp. Discoveries from non-repo users come back as low-confidence entries for review.
  • Foresight reminders: a daily GitHub Actions job posts a Teams card to the owning team before a risk lands, linked to the Chronicle entry.
  • CMDB or not: most CMDBs drift out of date because updating them is a separate chore nobody has time for. The Chronicle is kept current as part of the work itself. No CMDB? It stands on its own. Got one? Entries link to its records rather than copying them.
> HOW AN ENGAGEMENT RUNS

We work with your team, not at it. Your engineers know the environment; we bring the experience, the guardrails and a proven way of working. They're in the pull requests and the Chronicle from day one, because it's built from their knowledge and they'll run it after we leave.

  1. Assess: access model, infrastructure-as-code coverage, desktop and ticketing tools, CMDB or not, and what's already written down. Every environment is different, so the plan is built around what you already have.
  2. Deliver: we build and roll it out alongside your team, starting where it pays off first: ticket history, infrastructure discovery, or pipelines and guardrails. Along the way: the Chronicle and skill, code and pipelines, identities and guardrails, and working AI workflows for incident triage, change prep and onboarding.
  3. Hand over: your team running it. The Chronicle, skills and code are yours. Optional ongoing curation: resolving conflicts, pruning stale entries, promoting confirmed facts.
